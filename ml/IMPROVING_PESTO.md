# Улучшение качества fine-tuned PESTO

Здесь сначала важно зафиксировать: **offline PESTO имеет доступ к будущей части сигнала, RT-модель не имеет**.

Offline CQT использует примерно центрированное окно `8192 samples ≈ 186 ms`. Для полного соответствия ему RT потребовалось бы около `88 ms` lookahead. Сейчас эта правая часть заменяется `refill` или нулями. Fine-tuning может научиться лучше переносить артефакты, но не способен восстановить ещё не пришедшую информацию. Полностью закрыть разрыв без компромисса по latency, вероятно, невозможно.

## Почему текущий fine-tune ограничен

1. **Нет абсолютной цели pitch.**  
   Текущие invariance/equivariance losses требуют согласованности и правильного относительного сдвига, но напрямую не говорят: «этот кадр — E2».

2. **Нет временного обучения.**  
   `streaming_datamodule.py` выдаёт отдельные HCQT-кадры и перемешивает их. Encoder не видит последовательность, поэтому обучение не может явно уменьшать скачки, dropout и voiced flicker.

3. **Confidence вообще не обучается.**  
   Оптимизируются только `encoder.parameters()`. При экспорте confidence берётся из `mir-1k_g7`. Поэтому fine-tune pitch encoder не может исправить основную часть audible RT-проблем с гейтом.

4. **Лучший checkpoint выбирается по train loss.**  
   У нас нет validation loss, коррелирующего с F0 или слуховой оценкой. Минимальный self-supervised loss не обязательно означает лучший pitch.

5. **Метрики условны по voiced-кадрам.**  
   Модель может показывать хорошую pitch accuracy на тех кадрах, где она что-то выдала, но пропускать сложные участки. На слух dropout часто заметнее улучшения MAE.

6. **Сравнение пока не полностью чистое.**  
   Baseline использует `.8/zeros`, fine-tuned — `1/refill`. Часть разницы может идти от preprocessing, а не весов.

## Приоритет 1: teacher-student distillation

Самый логичный вариант, поскольку offline PESTO уже даёт хороший результат.

Для одного WAV:

```text
полный WAV → offline PESTO → teacher activations/F0/confidence
чанки 10 ms → streaming CQT → student encoder/confidence
```

Loss можно собрать так:

\[
L =
L_{KL}(p_{student},p_{teacher})
+ \lambda_f L_{Huber}(F0_s,F0_t)
+ \lambda_c L_{confidence}
+ \lambda_\Delta L_{temporal}
\]

Где:

- `KL` сопоставляет полные pitch-распределения, а не только итоговую частоту;
- F0-loss считается в центах на уверенных teacher-кадрах;
- confidence-head учится повторять offline confidence или RMS/pseudo-label;
- temporal loss сопоставляет изменения F0 между соседними кадрами.

Это непосредственно оптимизирует разницу **offline → streaming**, а не косвенные self-supervised свойства.

## Приоритет 2: дообучать confidence

Нужно добавить `ConfidenceClassifier` в training module и обучать его отдельно.

Варианты разметки:

- offline confidence как soft target;
- RMS activity как слабая разметка;
- комбинация RMS, offline confidence и ручной фильтрации;
- positive/negative примеры: ноты, паузы, шум, затухания, приглушённые струны.

На inference добавить hysteresis:

```text
voiced включается при confidence > 0.6
voiced выключается при confidence < 0.4
```

Также полезны:

- минимальное время удержания voiced;
- короткий grace period при confidence-dropout;
- разные пороги для attack и sustain.

Это, вероятно, даст более заметный слуховой эффект, чем дальнейшее уменьшение MAE на несколько cents.

## Приоритет 3: обучаться последовательностями

DataLoader должен возвращать не отдельный кадр, а последовательность, например:

```text
16–32 кадров = 160–320 ms
```

Тогда можно добавить:

- штраф за скачки >50 cents;
- штраф за неожиданные октавные переходы;
- loss на производную F0;
- loss на voiced-toggle;
- отдельный attack loss;
- соответствие временной динамике offline teacher.

Encoder сейчас независимый покадровый. Можно начать без изменения архитектуры, просто считать temporal loss между последовательными выходами. Позже можно добавить небольшой causal TCN поверх pitch activations.

## Приоритет 4: настоящий lookahead

Проверить несколько задержек:

| Lookahead | Samples | Ожидаемый эффект |
|---|---:|---|
| 0 ms | 0 | текущая минимальная latency |
| 20 ms | 882 | заметно больше данных атаки |
| 40 ms | 1764 | вероятно существенно стабильнее |
| ≈88 ms | ≈3875 | близко к offline CQT |

Для записи в DAW можно сообщать latency через VST delay compensation. Для live monitoring 88 ms слишком много, но `20–30 ms` могут оказаться приемлемым компромиссом.

Практический вариант: намеренно задерживать начало синтезированного баса на `20–30 ms`, зато не выпускать неправильную ноту на атаке.

## Приоритет 5: адаптировать frontend под E2–E4

Текущий CQT начинается с `27.5 Hz`, поэтому kernel имеет ширину `8192 samples`. Но детектору нужны только гитарные `82–330 Hz`.

Возможные изменения:

- поднять `fmin`;
- убрать ненужные низкие CQT bins;
- использовать более короткий kernel;
- переобучить или адаптировать первый/последний слои.

Это может уменьшить требуемый контекст и сделать causal streaming проще. Но совместимость с pretrained Toeplitz weights придётся аккуратно сохранять или переобучать.

## Приоритет 6: более консервативный fine-tune

Для первых supervised/distillation экспериментов:

1. заморозить ранние Conv1d-слои;
2. обучать только `ToeplitzLinear` и confidence;
3. затем постепенно размораживать encoder;
4. использовать небольшой LR;
5. добавить regularization к исходным весам или KL к исходной offline-модели.

Это уменьшит риск разрушить уже хорошие pitch-признаки.

## Что проверить до нового обучения

Перед изменением модели я бы провёл два обязательных теста:

1. Экспортировать baseline и fine-tuned с одинаковыми `mirror/mirror_fn`.  
   Иначе нельзя отделить эффект весов от preprocessing.

2. Сравнить Python ONNX и C++ покадрово на одном WAV.  
   Нужно сохранить из C++ `f0`, confidence и cache/reset-события. Если Python streaming ONNX звучит лучше C++, проблема находится в интеграции, и fine-tune её не исправит.

## Рекомендуемый план

1. Проверка Python ONNX ↔ C++ parity.
2. Чистый benchmark всех моделей с одинаковым streaming frontend.
3. Distillation streaming student от offline PESTO.
4. Обучение confidence-head.
5. Hysteresis и dropout hold.
6. Эксперимент с lookahead `0/20/40 ms`.
7. Только после этого — temporal architecture или новый CQT frontend.

Наиболее вероятный практический выигрыш дадут **distillation + confidence training + небольшой lookahead/hysteresis**. Текущие self-supervised losses сами по себе плохо соответствуют тем дефектам, которые наиболее заметны на слух.
