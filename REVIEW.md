## 🔴 Critical — фактические ошибки и расхождения с кодом

### C1. §5 «Минусы Phase 1»: тишины на первые 21 мс нет

**Локация:** RESEARCH.md, строка 344, секция «5. Подход A: Rule-based синтез — Минусы»

**Сейчас:**
> «Тишина на первые ~21 мс (`pitchIsValid=false`)»

**Проблема:** В `src/PluginProcessor.cpp:72-73` при `pitchIsValid=false`
выполняется `return;` *до* dry/wet микса — буфер остаётся неизменным,
**гитара проходит в выход без обработки**. Это dry-passthrough, не тишина.
Ошибка концептуально важна: пользователь слышит свою гитару, а не молчание.

**Исправление:**
```diff
- Тишина на первые ~21 мс (`pitchIsValid=false`)
+ Dry-passthrough на первые ~21 мс (`pitchIsValid=false`) — гитарист
+ слышит свой сигнал, не молчание. Минус: при включённом мониторинге через
+ плагин гитара пробивается в первый бит, что субъективно воспринимается как
+ артефакт «гибридного» звука, особенно если dryWet=1.0.
```

### C2. §4.1 и §2.3: Boss OC-2 ≠ «нулевая задержка»

**Локация:** RESEARCH.md, строка 233 (§4.1) и строка 138 (§2.3)

**Сейчас:**
> «Boss OC-2 (аналог, 1982) … Нулевая задержка»
> «Аналоговый октавер (Boss OC-2): триггерит D-флип-флоп по нулевым переходам»

**Проблема:**
1. OC-2 имеет минимальную задержку — флип-флоп требует *минимум одного
   полупериода* для смены состояния. Для E2 (82 Гц) это 6 мс, для E1
   (41 Гц) — 12 мс. «Нулевая задержка» — миф.
2. OC-2 использует не цифровые D-flip-flop, а аналоговые компараторы +
   делители частоты (CD4013-style), реализованные в дискретной аналоговой
   схеме. Это не «по сути цифровая операция», а нелинейный элемент в
   аналоговом тракте.

**Исправление:**
```diff
- Аналоговый делитель частоты. Нулевая задержка, но синтетический звук,
- работает только на чистом монофонном сигнале.
+ Аналоговый делитель частоты на компараторах. Минимальная задержка
+ — один полупериод входного сигнала (~6 мс для E2, ~12 мс для E1),
+ синтетический звук, требует чистого монофонного сигнала.
```

И в §2.3:
```diff
- Аналоговый октавер (Boss OC-2): триггерит D-флип-флоп по нулевым переходам
- сигнала — это деление частоты на 2, чисто цифровая (по сути) операция
- над временными метками.
+ Аналоговый октавер (Boss OC-2): компаратор детектирует нулевые переходы,
+ аналоговый делитель частоты (CD4013-style) формирует сигнал на f₀/2 — это
+ нелинейная операция (компаратор) внутри аналогового тракта, не линейная
+ фильтрация.
```

### C5. §12.4: Арифметика латентности в Phase 2A не сходится

**Локация:** RESEARCH.md, строки 672-682

**Сейчас:**
```
  Компонент                   Phase 1    Phase 2A target
  ────────────────────────────────────────────────────────
  YIN / PESTO window          21 мс      < 5 мс
  ML inference                —          5–15 мс
  processBlock buffer         5–10 мс    5–10 мс
  Алгоритмическая задержка    0 мс       0–30 мс (DAW компенсирует)
  ────────────────────────────────────────────────────────
  Итог RT мониторинг          21 мс      < 30 мс ✓
```

**Проблема:** Сумма для Phase 2A: 5 + 5 + 5 + 0 = 15 мс минимум,
5 + 15 + 10 + 30 = 60 мс максимум. «< 30 мс» — это нижняя граница, а
не итог. Также пункт «Алгоритмическая задержка» дублирует то, что уже
учтено в processBlock buffer и pitch window. Таблица некорректна.

**Исправление:** Развести «латентность мониторинга» (то, что слышит
гитарист в реалтайме) и «латентность записи в DAW» (которая компенсируется
через `setLatencySamples`).

```diff
   Компонент                   Phase 1     Phase 2A target
   ─────────────────────────────────────────────────────────
-  YIN / PESTO window          21 мс       < 5 мс
+  Pitch detection window      21 мс (YIN) <5 мс (PESTO)
   ML inference                —           5–15 мс
   processBlock buffer         5–10 мс     5–10 мс
-  Алгоритмическая задержка    0 мс        0–30 мс (DAW компенсирует)
+  Алгоритмический lookahead   0 мс        0–30 мс (только в записи,
+                                          DAW компенсирует)
   ─────────────────────────────────────────────────────────
-  Итог RT мониторинг          21 мс       < 30 мс ✓
-  Итог запись (DAW comp.)     21 мс       < 60 мс ✓
+  RT мониторинг (sum)         26–31 мс    15–30 мс ✓
+  Запись (после DAW comp.)    ~0 мс       ~0 мс ✓
```

Уточнение: PluginProcessor.cpp сейчас НЕ вызывает `setLatencySamples()` —
DAW компенсация *не работает*. Это надо отметить отдельно (см. G4).

### C6. §4.4: «Проблема всех решений — одна и та же» — фактически неверно

**Локация:** RESEARCH.md, строка 276

**Сейчас:**
> «Проблема всех решений — одна и та же:
>  Детектор → Не знаю питч → Молчит / держит старый питч»

**Проблема:** EHX POG/POG2 принципиально *не используют* pitch detection —
гранулярный/phase-vocoder подход просто пересэмплирует буфер на ±N
полутонов без определения F0. Их проблема — «watery attack» из-за окна
FFT, не «не знаю питч». Это явно противоречит §4.3 (строка 308) где
написано «EHX POG (phase vocoder) … Глитч: Обойдена … pitch detection отсутствует».

**Исправление:**
```diff
- Проблема всех решений — одна и та же:
+ Проблема pitch-tracking решений (Boss OC-2, Guitar Rig, Ampero) — одна и та же:

  Детектор              Синтезатор
  ────────              ──────────
  "Не знаю питч"   →   Молчит / держит старый питч

  Причина: период баса = 12–24 мс, нужно 3 периода → задержка 36–72 мс

+ EHX POG (granular/phase-vocoder) обходит pitch detection, но платит
+ другую цену — «watery» атаки от FFT-окна.
```

### C7. Sample rate несоответствие: 48 кГц в RESEARCH vs 44.1 кГц в проекте

**Локация:** RESEARCH.md строки 86, 681 (и далее упоминания «48 kHz»)

**Исправление:** Добавить в §2.1 явное замечание:

```diff
+ **Замечание о sample rate.** Проект использует 44.1 кГц (зафиксировано
+ датасетом). При 44.1 кГц окно 1024 сэмплов = 23.2 мс, и для E2 (82 Гц,
+ период 12.2 мс) это лишь ~1.9 периода — на грани требования YIN.
+ Для надёжной детекции E2 желательно окно 1536 сэмплов (~35 мс), либо
+ переключение на PESTO/SwiftF0 в Phase 2.
```

### M4. §2.3 «нет в гитарном сигнале» — упрощение

**Локация:** RESEARCH.md, строки 113-115 и сворачиваемый блок «теория»

**Сейчас:**
> «F₀/2 — это субгармоника, которой в гитарном сигнале нет вообще»

**Проблема:** Утверждение слишком сильное. У гитары на нелинейном
тракте (усилитель, дисторшн, насыщение) **могут** появляться
субгармоники из-за параметрических эффектов. Также в чистом сигнале
существует слабая F₀/2 от:
- ангармоничности струны (frequency-dependent inharmonicity)
- modal coupling между струнами через бридж

Уровень обычно <-60 дБ относительно фундаментала, но «нет вообще» —
неточно. Формулировка корректна для линейной модели, но в физике
тонкая струна — слабо нелинейный объект.

**Исправление:** Смягчить формулировку.

```diff
- F₀/2 — это субгармоника, которой в гитарном сигнале нет вообще.
- Её нельзя создать линейным фильтром.
+ F₀/2 — субгармоника, **практически отсутствующая** в чистом гитарном
+ сигнале (типичный уровень <-60 дБ от F₀ за счёт слабой нелинейности
+ струны и связности мод). Её нельзя создать линейным фильтром, и она
+ ниже шумового пола трактов, поэтому для синтеза баса её нужно
+ **сгенерировать заново**.
```

### M8. §7 «TCN stateless → артефакты» — спорное обобщение

**Локация:** RESEARCH.md, строки 213-215

**Сейчас:**
> «TCN … Stateless: каждый буфер обрабатывается независимо. Проблема для нашей задачи: фаза субгармоники F₀/2 между соседними чанками не синхронизирована → слышны артефакты "дёргания".»

**Проблема:** Это **не** проблема самой архитектуры TCN, а **артефакт
дефолтного применения** stateless TCN с независимыми буферами. Стандартное
решение — **streaming TCN с кэшированием** входных активаций между
буферами (это как раз то, что делают amp-sim плагины на TCN-движках).

То есть TCN можно использовать stateful'но через ring-buffer входов
(receptive field overlap). Архитектурно фаза становится когерентной —
проблема не у TCN, а у *неаккуратной* реализации.

**Исправление:**

### N3. §8 «CMNDF на autocorrelation» — терминологическая неточность

**Локация:** RESEARCH.md, строка 473

**Сейчас:**
> «CMNDF на autocorrelation»

**Проблема:** YIN не использует автокорреляцию. YIN использует
**squared difference function** d(τ) = Σ(x[j] - x[j+τ])², на которой
строится CMNDF (cumulative mean normalised difference function).
Squared difference и autocorrelation **связаны** (d(τ) = 2r(0) - 2r(τ) для
бесконечного сигнала), но это разные шаги.

**Исправление:**
```diff
- CMNDF на autocorrelation. Требует 2–3 полных периода → задержка 18–36 мс на гитаре.
+ CMNDF на squared difference function (не на autocorrelation, хотя они
+ математически связаны). Требует 2–3 полных периода → задержка 18–36 мс на гитаре.
```

### N5. §2.1 «нужно 2-3 периода» — упрощение для YIN

**Локация:** RESEARCH.md, строки 63-64

**Сейчас:**
> «Чтобы определить F0 сигнала, нужно наблюдать хотя бы 2–3 полных периода. Это фундаментальное ограничение»

**Проблема:** «2–3 периода» — это эмпирика для autocorrelation методов.
Информационно-теоретическая нижняя граница: чтобы разрешить F0 с
точностью ε, нужно окно ≥ 1/(2ε·F0) (Heisenberg time-frequency). Для
гитары F0 = 82 Гц с точностью ±5 Гц это даёт ~10 мс — меньше «2-3
периодов». Но для **робастной** детекции в шуме нужно действительно
больше периодов.

**Исправление:** Уточнить, что 2-3 периода — практическая граница для YIN
и autocorrelation, не теоретическая.

```diff
- Чтобы определить F0 сигнала, нужно наблюдать хотя бы **2–3 полных периода**.
- Это фундаментальное ограничение — меньше просто нечего анализировать.
+ Для **робастной** детекции через autocorrelation/YIN нужно окно
+ ≥ 2 полных периодов (информационно-теоретический минимум — около 1
+ периода, но на нём YIN неустойчив к шуму). Это практический предел —
+ меньше анализатору надёжно нечего сказать.
```
